Sistema local que automatiza a prospecção de clientes da BrandForge no Instagram, seguindo o ciclo Observar → Decidir → Agir → Medir → Aprender → Adaptar. Especificação completa em [prompt.MD](prompt.MD).

- **Etapa 11 — Trava e handoff de canal** implementada em [src/features/campaigns/channel-lock.ts](src/features/campaigns/channel-lock.ts):
  - `tryTransitionChannelState(leadId, from, to, extra?)` é a trava de propriedade de canal de fato (prompt.MD "A trava de propriedade de canal impede envio simultâneo"): um único `UPDATE ... WHERE id = ? AND channel_state IN (...)`, que o SQLite serializa entre processos — o worker (`tsx` standalone) e o painel Next.js (Server Actions) escrevem no mesmo arquivo `.db`, então a checagem "ler o estado, depois decidir, depois escrever" de antes (etapas 9-10) tinha uma janela de corrida real entre processos, não só teórica. `from` aceita um estado ou lista; `extra` deixa setar outros campos (hoje só `pipelineStage`) atomicamente junto com a transição. Retorna `false` quando a linha não estava mais no estado esperado — "perdeu a corrida", tratado como no-op em todo lugar, nunca como erro nem como "tenta de novo com o estado antigo".
  - [outreach.ts](src/features/campaigns/outreach.ts) (`send_browser_dm`): depois de passar pelas checagens de ritmo (janela de operação, limite diário, intervalo mínimo), reserva o canal com CAS `browser_contact_pending` → `browser_contact_sent` **antes** de mandar a mensagem — é o uso do estado `browser_contact_sent` do enum que a etapa 9 documentou como pulado, agora usado como reserva de "estou enviando agora". Perdeu a reserva → evento `channel_lock_lost`, no-op. Falha ao enviar → reverte a reserva (`browser_contact_sent` → `browser_contact_pending`, best-effort: só desfaz a própria reserva, nunca sobrescreve um estado que o operador tenha setado nesse meio-tempo) antes de relançar para o retry normal. Sucesso → CAS `browser_contact_sent` → `waiting_inbound_reply` (com `pipelineStage: "contacted"` junto, no mesmo UPDATE).
  - [inbound.ts](src/features/campaigns/inbound.ts) (`poll_webhook_inbox`): o handoff `waiting_inbound_reply`/`browser_contact_sent` → `api_active` agora é CAS a partir do estado exato lido para aquele lead — se uma reserva de `send_browser_dm` venceu a corrida entre a leitura e o handoff, o handoff perde e grava `channel_lock_lost`, mas a mensagem inbound e o avanço de `pipelineStage` (`contacted` → `replied`) acontecem de qualquer forma (não dependem de ganhar o canal).
  - [api-outreach.ts](src/features/campaigns/api-outreach.ts) (`send_api_message`): o fechamento da janela de mensageria (`api_active` → `api_window_closed`) virou CAS. Antes de despachar pela Graph API, uma segunda checagem CAS `api_active` → `api_active` (uma verificação, não uma mudança de valor) reconfirma que a propriedade do canal não mudou entre a leitura do lead e o envio de fato — perdeu → `channel_lock_lost`, no-op, não tenta contornar pelo navegador (prompt.MD "não tentar contornar pelo navegador").
  - `EVENT_TYPES` ganhou `channel_lock_lost`; schema + label PT-BR ("Disputa de canal perdida"), sem migração (mesmo motivo dos eventos anteriores: `events.type` é `text` sem `CHECK`).
  - Não existe (e não foi pedido) um lock que abranja toda a duração do envio pela API — a reconfirmação em `api-outreach.ts` reduz a janela de corrida para o instante antes do `fetch`, não a elimina por completo, porque o enum de `channelState` do prompt.MD não tem um estado "enviando pela API" reservável como `browser_contact_sent` tem para o navegador. Inventar um exigiria mudar o enum do prompt.MD sem pedido do usuário.
  - Testes: [channel-lock.test.ts](src/features/campaigns/channel-lock.test.ts) (CAS ganha/perde, array de `from`, `extra` só aplicado quando a transição vence) e casos de "perdeu a corrida" adicionados em [outreach.test.ts](src/features/campaigns/outreach.test.ts) e [inbound.test.ts](src/features/campaigns/inbound.test.ts) via mock de `tryTransitionChannelState`.

## Stack

Next.js (App Router) · React · TypeScript `strict` · Tailwind · SQLite · Drizzle ORM · Node.js 24 LTS · pnpm · Playwright (via CDP) · SDK oficial da OpenAI.

Monolito modular — sem microservices, sem Redis/Postgres/Elasticsearch no MVP.

## Convenções

- **Interface em PT-BR.** Código (arquivos, variáveis, funções, tabelas, status internos, commits) **em inglês.**
- Ler config de negócio de `config/business.json` — nunca hardcode dado real no código.
- IA só pode enviar o que está em `verifiedClaims`. Tudo em `unverifiedClaims` é bloqueado, sem paráfrase.
- Clean code: funções pequenas, sem `any`, sem abstração especulativa, sem Clean Architecture cerimonial.
- Pipeline (funil) e canal (navegador/API) são campos de estado **separados** — ver seção "Estados" do [prompt.MD](prompt.MD).

## Comandos

- `pnpm dev` — sobe só o painel Next.js.
- `pnpm worker` — sobe só o worker (loop de jobs duráveis).
- `pnpm dev:all` — sobe painel e worker juntos.
- `pnpm build` / `pnpm lint` / `pnpm typecheck` — build de produção, ESLint e `tsc --noEmit`.
- `pnpm db:generate` — gera migração Drizzle a partir de `src/db/schema.ts`.
- `pnpm db:migrate` — aplica migrações no arquivo apontado por `DATABASE_URL` (padrão `data/brandforge.db`, pasta gitignored).
